## Phase Boundary

Post-verification gap-closing insertion after Phase 40 (which stays VERIFIED
human_needed). It bundles two unrelated cleanup workstreams surfaced by the
v0.6.0 milestone audit + Phase 40 verification. No new user-facing capability;
this closes a residual resume-path gap and lands non-blocking Phase 38 CR/WR
advisories. Phase 40 itself is NOT reopened — its source + CPU guards stay
GREEN; the 3 PRESENT_BEHAVIOR_UNVERIFIED truths (DMV3-07 runtime, DMV3-08
resume runtime, DMV3-10 CI GREEN) remain deferred to the `dreamer-gpu` CI job
per INV-8, gated on the same standalone GitHub-GPU-runner enablement action
item (unchanged by this phase).

**What this phase delivers:**

1. **DMV3-08 `checkpoint_dir` resume gap (dreamer):** `_find_latest_checkpoint`
   in `src/surg_rl/dreamer/training.py:183-198` hardcodes
   `models/dreamerv3/{task}_{obs_type}` and ignores the `checkpoint_dir` the
   parent already resolved (`training.py:236-237`) and threaded to the child
   (`training.py:259`). The two call sites (`training.py:282`, `:299`) pass
   only `task, obs_type`, so with a custom `checkpoint_dir` + `resume=True`
   the parent's `subprocess.load_checkpoint(latest)` never fires
   (`latest=None`). Today this is masked by the child's `cp.load_or_save()` at
   construct (`subprocess.py:217`). This phase threads `checkpoint_dir` into
   `_find_latest_checkpoint` and the two call sites so the parent resume path
   actually finds checkpoints at a custom dir — fixing the fragile
   defense-in-depth gap the audit names
   (`v0.6.0-MILESTONE-AUDIT.md:48-49, 152`).

2. **Phase 38 advisory cleanups (fluids):**
   - **CR-01 (already fixed, test the remaining gap):** the `np.gradient` cell-
     spacing fix is already committed (`cc117c3 fix(38): CR-01 pass physical
     cell spacing to np.gradient`, `force_computation.py:67-69`). The
     remaining CR-01 follow-up is the **physical-magnitude regression test**
     `38-REVIEW.md` recommended, which does not yet exist (the closest test,
     `test_3d_force_y_axis_nonzero`, only asserts `fy > 0.0`).
   - **WR-01 / WR-02 (inert knobs → implement, not remove):** `coupling_mode`
     (ONE_WAY/TWO_WAY) and `coupling_substeps` are validated + tested but
     never consumed by `FluidSimulator.step` (`fluid_simulator.py:182-235`) —
     both modes run byte-identical code. This phase IMPLEMENTS real TWO_WAY
     obstacle-velocity feedback into the `make_incompressible` boundary (per
     Phase 38 D-10) + a real substep loop, rather than removing the fields.
     This elevates the fluids portion from "cleanup" to "cleanup + real
     behavioral feature" — a deliberate scope choice confirmed in discussion.

**What this phase does NOT deliver:**
- Reopening Phase 40 verification or re-running the `dreamer-gpu` CI job —
  that job + the GitHub GPU runner enablement stay a standalone ops action
  item (STATE.md USER ACTION ITEM), unchanged.
- Removing `coupling_mode` / `coupling_substeps` (the alternative
  disposition) — explicitly NOT chosen; implementation is locked (D-04).
- A change to the `dreamerv3~=1.5.0` pin, the JSON-over-stdio subprocess
  protocol, the `DreamerConfig` schema `obs_type ∈ {pixels, state}` surface,
  or the 2D `compute_obstacle_forces` path (the CR-01 fix is 3D-only; the 2D
  path already divides by `dx`/`dz` correctly).
- Convergence-threshold assertions, additional `obs_type` values, or the
  other 4 Phase 38 advisories (WR-03 tip absorbed, WR-04 zero-y bounds,
  WR-05 zip strict [already fixed by `77a8e71`]) — out of scope here.

<decisions>
## Implementation Decisions

### DMV3-08 checkpoint_dir threading (dreamer)
- **D-01:** Thread `checkpoint_dir` into `_find_latest_checkpoint` so the
  parent resume path finds checkpoints at a custom directory. The two call
  sites (`training.py:282` eval_only branch, `training.py:299` resume branch)
  pass the parent-resolved `checkpoint_dir`. Exact signature shape is
  Claude's discretion (e.g. `_find_latest_checkpoint(task, obs_type,
  checkpoint_dir=None)` with checkpoint_dir overriding the derived default, or
  `_find_latest_checkpoint(checkpoint_dir)` with the caller always passing the
  resolved dir) provided the custom-dir resume path is wired and the default
  dir (`models/dreamerv3/{task}_{obs_type}`) behavior is preserved when no
  custom dir is given.
- **D-02 (resume contract — defense-in-depth):** Keep BOTH resume layers
  active — the now-wired parent path (`_find_latest_checkpoint` →
  `subprocess.load_checkpoint`) AND the child's `cp.load_or_save()` at
  construct (`subprocess.py:217`). Both resume from the same
  `checkpoint.ckpt`. Do NOT remove the child auto-resume to make the parent
  sole source of truth. This is the audit's "fix the defense-in-depth gap"
  reading — make both layers work; the parent path is now wired + tested, the
  child stays as a safety net.
- **D-03 (verification):** Add a **CPU-runnable test with a subprocess stub**
  (no GPU, no JAX, no `pytestmark` skipif) that builds a fake
  `models/dreamerv3/{task}_{obs_type}/` dir with a `checkpoint.ckpt`, calls
  `_find_latest_checkpoint` with a custom `checkpoint_dir` (asserts it
  returns that path; returns `None` when the custom dir is empty), AND
  stubs `DreamerSubprocess` to assert `run_dreamer_training(resume=True,
  checkpoint_dir=<custom>)` actually calls `subprocess.load_checkpoint` with
  the custom path. Exercises the full parent resume path, not just the glob
  helper. Complements (does not replace) the existing GPU-gated
  `test_dreamerv3_checkpoint_resume.py`.

### CR-01 physical-magnitude regression test (fluids)
- **D-04:** The CR-01 `np.gradient` cell-spacing fix is already committed
  (`cc117c3`); this phase does NOT re-fix it. Add the **physical-magnitude
  regression test** `38-REVIEW.md` recommended: a linear pressure ramp of
  known slope produces `F = -∇p · V_mask` within a tolerance. Hand-compute
  the expected `fy` from `dy` and the ramp slope (e.g. for
  `p[i,j,k] = j/ny` on a 0.3m / 16-cell domain, `dy ≈ 0.01875`, `grad_y` per
  meter known) and assert within ~1%. This is a NEW test, separate from
  `test_3d_force_y_axis_nonzero` (which stays as the "path exercised / fy
  nonzero" check). Pins that the fix actually produces Newtons, not
  cell-index units — a future change re-breaking units is caught.

### WR-01/WR-02 inert coupling knobs (fluids) — implement, not remove
- **D-05 (disposition):** IMPLEMENT real TWO_WAY + substeps. Do NOT remove
  `coupling_mode` / `coupling_substeps` / `FluidCouplingMode` / their tests.
  `FluidSimulator.step` gains (a) real TWO_WAY obstacle-velocity feedback
  into the `make_incompressible` boundary condition (per Phase 38 D-10),
  gated on `config.coupling_mode == FluidCouplingMode.TWO_WAY`, and (b) a
  real substep loop. This makes the opt-in knob the config surface promises
  actually behave as documented. (Removing was the "cleanup" default;
  implementation is the confirmed scope choice — it makes this a behavioral
  feature, not just a cleanup.)
- **D-06 (substep scope + dt):** The substep loop runs for **BOTH ONE_WAY and
  TWO_WAY** (the field description says "on the 3D obstacle path", not
  TWO_WAY-only). `sub_dt = dt / coupling_substeps` (38-REVIEW's version, NOT
  the field's "reuses substep_dt as per-substep dt" phrasing — the planner
  should update the field description to match). Default
  `coupling_substeps` stays `4`, so ONE_WAY now does 4 sub-solves per step —
  this changes ONE_WAY timing, but existing stability tests
  (`test_one_way_stable_n100`) assert finiteness only, so they still pass. If
  the planner finds ONE_WAY substepping destabilizes an existing test, raise
  it — do not silently special-case ONE_WAY to skip the loop.
- **D-07 (TWO_WAY xfail test disposition):** Replace the current
  `test_two_way_opt_in_documented_unstable` with **TWO tests**: (a) a
  CPU-cheap **structural** test asserting TWO_WAY `step()` actually takes the
  feedback branch (obstacle velocity appears in the `make_incompressible`
  boundary) — stable, no xfail; (b) keep an `@pytest.mark.xfail(strict=False)`
  for the thin-instrument divergence case, which now GENUINELY exercises the
  unstable added-mass path (it was falsely xpassing before because ONE_WAY
  == TWO_WAY). An xpass on (b) is now a real signal that the tested
  instrument dims happen to be stable — still "not a guarantee" per the
  existing docstring; keep that docstring wording.
- **D-08 (TWO_WAY feedback mechanism):** Feed obstacle velocity back into the
  `make_incompressible` boundary condition per Phase 38 D-10 (the
  added-mass-instability mechanism documented in RESEARCH Pitfall 8). Exact
  PhiFlow boundary expression is Claude's discretion, provided TWO_WAY
  diverges from ONE_WAY on thin instruments and the structural test (D-07a)
  can observe the feedback branch being taken.

### Phase structure
- **D-09 (plan shape):** **Two plans with no dependency**, runnable in a
  single parallel wave: **40.1-01** dreamer `checkpoint_dir` gap
  (`dreamer/training.py` + `tests/dreamer/` CPU resume test), **40.1-02**
  fluids advisories (CR-01 magnitude test + implement TWO_WAY + substep loop
  + structural/xfail tests in `fluids/` + `scene_definition/schema.py` field
  description). Each plan owns a **disjoint module set** (dreamer/ vs fluids/)
  — no file collisions, matches the GSD wave-based parallelization. NOT a
  single serial plan, and NOT a roadmap renumbering into two phases.

### Claude's Discretion
- Exact `_find_latest_checkpoint` signature shape (D-01) — additive param
  vs. caller-resolved-dir, provided the custom-dir resume path is wired and
  the default-dir behavior is preserved.
- Exact TWO_WAY feedback PhiFlow expression in `step()` (D-08), provided it
  diverges from ONE_WAY on thin instruments and the structural test observes
  the feedback branch.
- Exact physical-magnitude test fixture (ramp slope, domain size, mask
  geometry, tolerance) for the CR-01 regression test (D-04), provided it
  hand-computes `F = -∇p · V_mask` and asserts within a stated tolerance (not
  just `> 0`).
- Exact subprocess stub mechanism in the CPU resume test (D-03) —
  `unittest.mock` / monkeypatch / fake `DreamerSubprocess` subclass —
  provided it asserts `load_checkpoint` is called with the custom path.
- Whether to update the `coupling_substeps` field description text to match
  D-06's `dt / coupling_substeps` semantics (recommended — the current
  "reuses substep_dt" phrasing is now wrong-by-construction).

</decisions>
